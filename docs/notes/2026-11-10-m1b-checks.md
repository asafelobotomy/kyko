# Slice 1b checks (kykod 0.0.2)

Recorded on 2026-11-10 on the development machine (Manjaro, kernel 7.2.9, systemd user session).
Every run of `kykod` here used `--socket` with a path in a temporary folder, so the real
`$XDG_RUNTIME_DIR/kyko/hold.sock` was never touched. The transient units were stopped and removed
afterwards (`systemctl --user list-units 'kykod-check*' --all` lists nothing).

The client in checks 1, 2 and 5 is a short Python script that speaks the protocol as the tests'
`Client` does: `Hello`, one `Spawn` of `/bin/sh -c CMD`, wait for a marker in the output, close.

## End-to-end tests: one defect found and fixed

`apps/kykod/tests/end_to_end.rs` passed at its first run; no change to `kyko-term` was needed.

The speed check (check 4) did fail at first, and the cause was in `kykod`: one `Output` frame per
terminal read. `seq` writes a line at a time to a terminal, so `kykod` read and sent about 93
bytes per frame (191,555 frames for one 16.9 MB run). The fix, in `Pane::pump`: after a read,
whatever is already waiting is read into the same buffer (a `poll` with a zero timeout, up to the
64 KiB frame limit) before the frame goes out. Nothing waits for more output, so typing is not
delayed. The test `a_busy_pane_sends_output_in_few_frames` (`apps/kykod/tests/server.rs`) failed
before the fix (24,375 frames averaging 93 bytes) and passes after it (about 260 frames averaging
about 9 KB).

## Finding: the resize nudge did not make programs redraw (fixed)

The spec (§2.8) says a `Resize` with the pane's current size, sent after `Replayed`, makes
full-screen programs redraw. On Linux it did not: the kernel sends `SIGWINCH` only when a
terminal's size changes, and a same-size `TIOCSWINSZ` is a no-op. With `less` on screen, 0 bytes
of output followed the nudge, and the end-to-end test passed only because the replay alone rebuilt
`less`'s screen.

Fixed in the review's fix pass: the first same-size `Resize` after an `Attach` makes `kykod` send
`SIGWINCH` to the terminal's foreground process group itself (`killpg` on `tcgetpgrp` of the
master; `TIOCSIG` with `SIGWINCH` answers `EINVAL` on this kernel). Measured by the reviewer: `less`,
`vim`, `nano` and `top` redraw their whole screen; a shell at its prompt redraws nothing. The test
`a_same_size_resize_after_attach_makes_a_full_screen_program_redraw` now discards the replay and
requires the paged `less` screen from the redraw alone; it failed before the fix (a blank screen)
and passes after it.

## 1. The unit stops cleanly and takes the shells with it

```sh
systemd-run --user --unit=kykod-check1 -p Restart=on-failure -p KillMode=mixed -p TimeoutStopSec=5 \
    $PWD/target/release/kykod --socket /run/user/1000/kykod-check.HsBR/kyko/hold.sock
client.py .../hold.sock 1 armed1 'echo armed1; exec sleep 3071'
systemctl --user stop kykod-check1
```

(A first attempt with a socket under the session's scratch folder failed with "path must be
shorter than SUN_LEN", which is the right refusal; the checks then used `$XDG_RUNTIME_DIR`.)

The shell (`sleep 3071`, pid 1671827) was running under `kykod` (pid 1671821). `systemctl stop`
returned after 0.008 s; the shell was gone at once. Journal: `ending every session (SIGTERM):
hanging up 1 shell(s)`, then `exiting`. The unit ended `Result=success`, `ExecMainStatus=0`.
The socket file was removed; its lock file stays, as designed.

## 2. When kykod itself is killed, the shells end

a. As the plan says, `systemctl --user kill -s KILL kykod-check2` with an interactive `sh -i` in a
pane: `kykod` and the shell were both gone within 1 s. That command signals every process in the
unit's cgroup, though, so it kills the shell directly.

b. `systemctl --user kill --kill-whom=main -s KILL kykod-check2` (only `kykod`): the shell was gone
within 1 s as well. systemd may also have killed what was left in the cgroup once the main process
died, so c checks the hangup alone.

c. To see what the spec describes without systemd: `kykod` started from a shell, a pane running
`sh -i`, then `kill -9` on `kykod` alone. The shell was gone within 0.5 s: the terminal's master
side closed with `kykod`, so the shell, the session leader, got its hangup.

In a and b, `Restart=on-failure` started a fresh `kykod` (journal: `replaced a stale socket file`)
with no panes. The sessions are lost when `kykod` dies; that is what the spec says.

## 3. Another user cannot connect

No other user was used (no privilege escalation in these checks). The socket and its folder as
`kykod` made them:

```
drwx------ /run/user/1000/kykod-check.FjrD/kyko
srw------- /run/user/1000/kykod-check.FjrD/kyko/hold.sock
```

Owner and group of both: the user running `kykod`.

Another user cannot reach the socket through the 0700 folder, nor open it with its 0600 mode, so
`connect` is refused before `kykod`'s peer-uid check is reached. That check (`SO_PEERCRED` uid
must equal `kykod`'s) is covered by the unit test `only_the_same_user_may_connect` of
`peer_allowed` in `apps/kykod/src/server.rs`.

## 4. The hop bench

```sh
cargo test -p kykod --release --test hop_bench -- --ignored --nocapture
```

`seq 1 2000000` (16,888,896 bytes on a terminal), five runs each way, alternated, timed to the
shell's exit with all output received.

Before the fix (load average 0.32 before, 1.12 after):

| | runs | median |
|---|---|---|
| PTY read directly | 713.4, 726.1, 697.4, 727.5, 770.0 ms | 726.1 ms |
| through kykod | 914.7, 921.8, 933.1, 985.0, 962.1 ms | 933.1 ms |

Ratio 1.285: over the 1.15 limit. A second run gave 1.332.

Profile (`perf record -e cpu-clock:u -g`) and a frame count: 191,555 `Output` frames per run,
about 88 bytes each. Most user time was the test client's per-frame work (a fresh 64 KiB buffer
per receive, a `setsockopt` per receive) and `kykod`'s per-frame `poll`, `read`, encode and
`write`. Making the test client cheaper alone (reusing its buffer) made the ratio worse (1.458),
since a faster reader only took the frames smaller; that change was reverted. Larger socket buffers
were not tried: with frames this small the socket buffer is not what fills.

After the fix (fewer, larger `Output` frames, above), load average 1.35 when started:

| | runs | median |
|---|---|---|
| PTY read directly | 730.1, 748.1, 697.2, 722.0, 704.4 ms | 722.0 ms |
| through kykod | 806.9, 848.7, 767.0, 828.4, 776.0 ms | 806.9 ms |

Ratio 1.117: within 1.15. Other runs with the fix gave 1.100 to 1.133.

After the review's fix pass, in which each pane's reader also waits on its shell's pidfd, one run
gave a ratio of 1.136 (direct median 729.7 ms, through `kykod` 828.6 ms) with a 1-minute load
average of 3.16, which the bench now prints.

## Tests under a PID 1 that does not reap

A GitHub Actions job container's PID 1 is not an init: it never reaps orphans. There up to five
`kykod` tests failed, because shells and their jobs re-parented to PID 1 stayed zombies and the
test helpers counted a zombie as alive. Fixed three ways: the helpers count a zombie as gone,
`kykod` reaps every shell that has ended before it exits, and the CI and release job containers
run with `--init`.

The same conditions locally: each `kykod` test binary run as PID 1 of a new PID namespace, so
that orphans are re-parented to the test process, which reaps only its own children:

```sh
cargo test -p kykod --locked --no-run --message-format=json   # for the binaries' paths
unshare --user --map-root-user --pid --fork --mount-proc target/debug/deps/<test binary>
```

Before the fix: `ending` failed 3 or 4 of 12 (`forced_end_sessions_overrides_busy`,
`sigterm_hangs_up_the_shells`, `end_sessions_and_sigterm_together_end_once`, and in one run
`end_sessions_with_idle_shells_exits_0_and_ends_them`, each "outlived kykod"), and `pty` failed
`hangup_ends_the_shell_and_its_children` ("the sleep outlived its shell"). With only `kykod`'s
reaping in place (the helpers still counting zombies), the shells' own failures were gone and
the failures left were those of the shells' children, which `kykod` cannot reap. After the fix,
every test binary passed there: lib 5, cli 2, attach 13, end_to_end 8, ending 13, pty 18,
server 35.
