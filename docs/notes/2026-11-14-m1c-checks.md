# Slice 1c checks (kykod 0.0.3)

Recorded on 2026-11-14 on the development machine (Manjaro, 8 cores). The machine was busy with
unrelated builds throughout (1-minute load average 11 to 43), which matters for the timings below.

## Tests

- `cargo test --workspace`: all pass (fmt and clippy `-D warnings` clean).
- **Differential test** (`apps/kykod/tests/modes_differential.rs`): random streams from a
  vocabulary of every tracked sequence, ignored ones, overflowing and aborted sequences,
  unterminated strings and broken UTF-8, fed to `Modes` in random chunks. The emulator rebuilt
  from the preamble alone matched the one fed the stream, including both kitty stacks (probed with
  pops and screen switches), for 200,000 streams. CI runs 10,000.
- **Checking the checker:** three bugs planted one at a time in `Modes` were each caught: treating
  47 as the alternate screen (seed 10), clearing the mouse mode on any unset (seed 1), and not
  rebuilding the alternate screen's kitty stack while the main screen is current (seed 119, at a
  probe). The last was a real bug in the first draft, found by reasoning before the test ran and
  confirmed by it.
- **End to end** (`end_to_end.rs`): with a 256 KiB ring and 400 KB drawn by cursor position with
  no line break, modes set before the cut survive a reattach, and modes cleared after it stay
  cleared. Both tests fail with the preamble removed from `Ring::replay`.

## Speed

**The scanner** (`modes_bench.rs`, best of five, 64 KiB chunks, load average 43):

| Output | MB | ms | GB/s |
|---|---|---|---|
| `seq`-like | 67.1 | 5.16 | 13.0 |
| `ls -l --color`-like (an SGR every line) | 67.1 | 140.2 | 0.48 |

**The ring's own cost** on the hop bench's output (`seq 1 2000000`, 16.9 MB, pushed in 9 KB
frames as `kykod` sends them; best of 15, the same scratch bench built from `main` and from this
branch, run alternately): `main` 1.68 to 1.78 ms, this branch 2.14 to 2.35 ms. The slice adds
about 0.5 ms per run, under 0.1% of a run through `kykod`.

**The hop bench** (`hop_bench.rs`), alternating `main` and this branch, load average 21 to 24:

| Build | Direct median | Through `kykod` | Ratio |
|---|---|---|---|
| `main` | 575.2 ms | 661.3 ms | 1.150 |
| this branch | 562.0 ms | 679.4 ms | 1.209 |
| `main` | 572.1 ms | 677.5 ms | 1.184 |
| this branch | 567.2 ms | 683.9 ms | 1.206 |

Under this load even `main` fails the 1.15 limit. The two builds' through-`kykod` medians differ
by 6 to 18 ms, about as much as `main`'s own two rounds differ (16 ms), and the ring's measured
cost is 0.5 ms.

**Rerun on a quieter machine** (later on 2026-11-14, after waiting for the 1-minute load average
to fall below 2; swap idle, CPU 95% idle between runs, `intel_pstate` with the `performance`
energy preference). Three runs of this branch at load 2.0 to 2.8 gave 1.424, 1.372 and 1.444
(direct medians 671 to 680 ms, through `kykod` 926 to 981 ms). `main` and this branch then
alternately, at load 4.4 to 4.5:

| Build | Direct median | Through `kykod` | Ratio |
|---|---|---|---|
| `main` | 681.6 ms | 1012.9 ms | 1.486 |
| this branch | 685.2 ms | 1051.6 ms | 1.535 |
| `main` | 684.8 ms | 982.2 ms | 1.434 |
| this branch | 705.9 ms | 1045.0 ms | 1.480 |

**The gate is not met, by `main` as much as by this slice.** `main` measured 1.10 to 1.13 on
2026-11-10 (slice 1b's note) and 1.43 to 1.49 now, on the same code, so something about the
machine changed, not kyko. Within a run, the five runs through `kykod` spread by up to 170 ms,
so the branch's 40 to 60 ms over `main` here is within the noise; the ring's own added cost was
measured directly at 0.5 ms. Why the hop costs more on this machine now than four days ago is
not known: memory, swap and the CPU's energy preference were checked and look normal. **Open:**
find out, and measure again, before relying on the hop bench as a gate. The version was bumped to
`0.0.3` at the user's request with this gate open.

## Live checks

Each program ran in a real `kykod` with a 256 KiB ring until the ring had wrapped, at 80 by 24.
A fresh `kyko-term` emulator (kitty keyboard on) then attached, fed the replay, sent the
same-size `Resize` nudge and read for 1.5 s. A throwaway harness, not committed.

| Program | Written | Modes after the replay | Screen |
|---|---|---|---|
| `vim -u NONE`, redrawing every 10 ms | 13.9 MB | alternate screen, cursor keys, keypad, bracketed paste, steady block cursor | whole, from the replay alone |
| `less`, paged with space and `g` | 1.7 MB | alternate screen, cursor keys, keypad | whole |
| `top -d 0.1` | 539 KB | cursor keys, keypad, hidden cursor (`top` does not use the alternate screen here) | whole after the nudge |
| `htop -d 1` | 397 KB | alternate screen, mouse 1000 with SGR encoding, cursor keys, keypad, hidden cursor | **partial**: see below |

No `U+FFFD` and no escape-sequence debris on any screen.

**Finding (not from this slice): `htop` does not repaint everything after the nudge.** Its
ncurses treats a same-size `SIGWINCH` as nothing to repaint, so only cells that change are drawn
again; the meter labels, the header row and the function-key bar stay missing until they change.
Slice 1b measured `less`, `vim`, `nano` and `top` redrawing fully. A fix belongs in `kykod`'s
nudge: after an attach, change the size by a row and back, which the kernel signals twice and
which makes ncurses repaint from scratch. Recorded in the release checklist.

## The alacritty bug: already fixed upstream, not yet released

Reproduced on 2026-11-14 against `alacritty_terminal` 0.26.0: a `Term` with
`Config { kitty_keyboard: true, .. }` fed `"\x1b[>1u"` 4097 times panics at `term/mod.rs:1296`
with `removal index (is 0) should be < len (is 0)`.

When it came to filing it, it turned out to be known and fixed: reported as
[alacritty/alacritty#8957](https://github.com/alacritty/alacritty/issues/8957) and
[alacritty/alacritty#9071](https://github.com/alacritty/alacritty/issues/9071), fixed by
[alacritty/alacritty#9073](https://github.com/alacritty/alacritty/pull/9073) (merged 2026-10-16,
commit `542147067dd016fc5f49120ef0ba605a98a4e3a7`), which removes from `keyboard_mode_stack`.
No crates.io release has it yet: 0.26.0 is still the newest. So nothing was filed. Before the
kitty keyboard option is turned on, take the first `alacritty_terminal` release after 0.26.0, or
pin that commit with a `[patch.crates-io]` git dependency.

## Deviations from the plan

- `Emulator::modes()` and `set_kitty_keyboard` moved from Task 3 into Task 1, so that the
  differential test ran from the start rather than only building.
- `find_start` prefers a line break only within the first 64 KiB of the kept bytes
  (`LINE_SEARCH`), so a full-screen program that writes no line break for megabytes does not lose
  its whole replay waiting for one.
- `less_after_the_wrap` became the live check above, as the review suggested.
- Task 3 Step 0 (the upstream report): not needed, the bug was already reported and fixed
  upstream (above).
